## D1 — Session state count: 21 (canonical)

- **Conflict.** Addendum §3.2 and §3.8 say the session statechart has "18 states"; the addendum's own reference `S` enum (§3.9) and the roadmap P7 ("`S` StrEnum of 21 states", exit criteria "all 21 states reachable") specify 21.
- **Decision.** The canonical count is **21 states** — exactly the set enumerated in the addendum §3.9 `S` StrEnum: `ARRIVAL, SPROUT_TEASE, DIAGNOSTIC, DISCOVERY, GUIDED_LEARNING, PRACTICE, EXPLANATION, SPROUT_SETUP, SPROUT_SETUP_HARD, TEACH_BACK, COACH_ASSIST, REFLECTION, INDEPENDENT_VERIFY, TRANSFER, MASTERY_DECISION, REWARD, SUMMARY, RETRIEVAL_SCHEDULE, COMPLETE, ESCALATE_TO_HUMAN, ABANDONED`.
- **Supersedes.** The "18 states" figures in addendum §3.2 and §3.8.
- **Consequence.** P7 exit criteria are unchanged. Any test, diagram, or dashboard that counts states uses 21.

## D2 — Embeddings: local `bge-small`, 384 dimensions, configuration-driven

- **Conflict.** v1.0 specifies `text-embedding-3-small` (1536-d) and hardcodes `vector(1536)` in the §22 DDL and table register; the addendum §7.2 replaces the model with local `bge-small` (384-d) but never reconciles the schema dimension.
- **Decision.**
  - Current embedding model: **local `bge-small`** (via `sentence-transformers`), per addendum §7.2. The two v1.0 RAG use cases and the "vectors never move a probability" rule are unchanged.
  - Current vector dimension: **384**.
  - The embedding model and its dimension MUST be **configuration** — a single settings source (Pydantic `BaseSettings`), consumed by the embedding worker and by the migration that creates the pgvector column. Neither value may be hardcoded in application code.
- **Supersedes.** The `vector(1536)` column definition in v1.0 §22 for implementation purposes. The v1.0 1536-d cost/config text remains valid only as the appendix cost model.
- **Consequence.** Swapping embedding models later is one config change plus an explicit re-embed migration; no code may assume 384 or 1536 literally. `bge-small` (384) is the seed value for that configuration.

## D3 — Diagnostician F1 bands

- **Conflict.** The ship gate is macro-F1 ≥ 0.75 (v1.0 §26, P6 exit), but the risk register triggers action at F1 < 0.70. Behavior between the two numbers was undefined.
- **Decision.** Measured on the 120-item golden set with the actual runtime model:
  - **≥ 0.75** — pass. Proceed; P6 exit criteria met.
  - **0.70 – 0.749** — **do not ship final diagnosis** on that configuration. Improve prompt, few-shot examples, and/or evidence representation, then re-measure. The gate is not met; the configuration is a development datapoint, not a shipping state.
  - **< 0.70** — **critical failure.** Diagnosis-dependent work does not proceed until fixed. The deterministic rule-based distractor→misconception fallback remains available for development and as the runtime fallback.
- **Consequence.** The 0.70 trigger in the risk register keeps its meaning (act immediately) without implying 0.70–0.749 is acceptable to ship.

## D4 — Voice latency: 1.3 s target, 2.0 s hard gate

- **Conflict.** v1.0 §18 targets ≤ 1.3 s perceived turn latency; roadmap P18 exit gate is ≤ 2.0 s p95; P30 restates 1.3 s target / 2.0 s gate. v1.0 also alerts at > 2 s.

## D6 — P2/P4 package homes: `packages/learning-engine` and `packages/llm` as new uv workspace members

- **Gap.** No canonical document names a directory for the roadmap P2 ("Deterministic Core") or P4 ("Provider Layer & ModelRouter") components. Roadmap P2 requires its functions to be "pure functions, no I/O, no framework coupling — **importable by tests, the service, and the eval harness alike**" (P2 Backend field). Roadmap P4 says only "`protege/llm/` package" without a parent directory.
- **Decision.**
  - `packages/learning-engine` — package `protege-learning-engine`, module `protege.learning_engine`. Owns P2's `answer_validator`, `mastery_engine`, `educational_validator`, `threshold_service`, `evidence_builder`.
  - `packages/llm` — package `protege-llm`, module `protege.llm`. Owns P4's `LLMProvider` protocol, `NvidiaProvider`, `FakeProvider`, `ModelRouter`.
  - Both are registered as `uv` workspace members alongside `services/session`, `packages/contracts`, `tools/authoring`, following the existing `packages/contracts` convention exactly (hatchling wheel build, `src/protege/<module>` layout, namespace package under `protege.*`).
- **Why this follows from the architecture.** Roadmap P24 (Evaluation Harness) will need to import the deterministic core and the provider layer without depending on FastAPI, SQLAlchemy, asyncpg, or uvicorn — those are `services/session`'s dependencies (`services/session/pyproject.toml`), not P2's or P4's. Nesting either package inside `services/session` would force `evals/` to depend on the entire session service to reuse pure math or a provider abstraction, which roadmap P2 explicitly forbids ("no framework coupling"). A sibling `packages/*` workspace member — the same shape `packages/contracts` already uses — keeps both new packages importable by the service, by `tools/authoring`, and by the future `evals/` package alike, with no framework weight.
- **Prevents.** Guessing the package location during P2/P4 implementation and having to move/rename `protege.learning_engine`/`protege.llm` later, which would touch every import site in P5–P9. It also prevents `packages/learning-engine` or `packages/llm` from accidentally acquiring a FastAPI/SQLAlchemy dependency by being co-located with the service.
- **References.** `PROTEGE_IMPLEMENTATION_ROADMAP.md` P2 ("Backend" field), P4 ("Backend" field), P24 ("Backend" field: "`evals/` package runnable as `make eval`"); `AGENTS.md` "Never create a second source of truth for state already represented elsewhere" (a nested copy of pure logic inside the service would risk exactly that).
- **Consequence.** `packages/learning-engine` and `packages/llm` exist from this point forward as empty, importable skeletons. Real P2/P4 logic and dependencies (SymPy, Hypothesis, the `openai` SDK) are added only on `feature/p2-learning` and `feature/p4-llm`, not here.

## D9 — Real NVIDIA integration tests are excluded from default CI

- **Gap.** Addendum §2.3 documents a hard **40 requests-per-minute** cap and a finite, exhaustible credit allowance ("your evaluation suite alone... consumes 300+" of a ~1,000-credit signup grant); roadmap P4's exit criterion requires "a round-trip call to a real NVIDIA model returns a schema-valid object" to be demonstrated, but no document says this call may run unconditionally in CI on every push/PR.
- **Decision.** Any test that performs a real network call to the NVIDIA endpoint is marked (e.g. a dedicated pytest marker such as `integration` or `external`) and is **excluded from the default `pytest` run** used by `make test` and the CI `backend` job (`.github/workflows/ci.yml`). It is invoked manually, or by an explicitly separate, deliberately-triggered job, never automatically on every commit.
- **Why this follows from the architecture.** Addendum §2.8's failure taxonomy and §2.3's mitigations ("Never demo with concurrent live users," "Cache every eval result to disk keyed by prompt hash") both treat the rate limit and credit budget as scarce, shared, easily-exhausted resources. `.github/workflows/ci.yml` currently runs `uv run pytest` unconditionally on every push to `main` and every pull request (`on: push/pull_request`); an unmarked real-model test would burn credits and risk the 40 RPM ceiling on every commit and every concurrent PR, which addendum §2.3's Day-1 action list is explicitly trying to protect against.
- **Prevents.** CI silently exhausting the NVIDIA credit allowance or tripping the 40 RPM limiter across concurrent PR runs, which addendum §2.3 identifies as a critical, build-ending risk (roadmap §3.3 risk register: "NVIDIA credits exhausted mid-build — Critical").
- **References.** `PROTEGE_ENGINEERING_ADDENDUM.md` §2.3, §2.8; `PROTEGE_IMPLEMENTATION_ROADMAP.md` P4 (Testing, exit criteria), §3.3 risk register; `.github/workflows/ci.yml` (`on: push/pull_request` triggers).
- **Consequence.** P4's real-model round-trip check is written but excluded from `[tool.pytest.ini_options]` default collection (or gated behind an explicit marker/opt-in flag) when P4 lands. This decision does not itself add the test — it constrains how P4 must add it.

## D10 — LOCKED: Elo update formula and Bayesian zero-likelihood handling

- **Status: LOCKED for P2 implementation (`feature/p2-learning`).** Supersedes the OPEN record this entry previously held (recorded during `feature/phase2-foundation`); both gaps below are resolved and implemented in `packages/learning-engine`.
- **Gap 1 — Elo (resolved).** `PROTEGE_ARCHITECTURE.md` §10.2 says only "Elo item difficulty, updated online (no cold-start item calibration needed)," with no K-factor or expected-score function specified anywhere. **Decision:** standard logistic Elo, per-item rating —

      E = 1 / (1 + 10 ** ((R_item - R_learner) / 400))
      R' = R + K * (S - E)

  with **K = 24**, declared once as `protege.learning_engine.constants.ELO_K_FACTOR` and never duplicated as a magic number. `update_item_elo` exposes `k` as an optional parameter purely so tests can exercise the formula at other values without hardcoding a second literal `24` — the shipped default is always `ELO_K_FACTOR`.
- **Gap 2 — Bayesian zero-likelihood (resolved).** §10.2 gives `P(M_k | d) ∝ P(d | M_k) · P(M_k)` with `P(d | M_k)` authored per misconception, but no document said what to do when an observed distractor `d` has no explicit entry in `Misconception.distractor_likelihood`. **Decision:** use the authored `"other"` entry as `P(d | M_k)` instead (matching the convention already present in authored content, e.g. the §38 worked example's `{"picks_1_8": 0.82, "says_equal": 0.06, "other": 0.12}`). If neither `d` nor `"other"` is authored, `misconception_belief_update` raises `UndefinedDistractorLikelihoodError` rather than inventing a value — that is authored-content misconfiguration, not a runtime numeric case to paper over. No hidden global epsilon, no probability clamping, no learned likelihoods: `P(d | M_k)` remains exactly what `packages/contracts`' `Misconception.distractor_likelihood` records.
- **Why this follows from the architecture.** `PROTEGE_ARCHITECTURE.md` §10.2 specifies the formulas and states `P(d|M_k)` is "AUTHORED, not learned"; it does not specify a K-factor or a missing-entry convention. Both values above are supplied verbatim by the task instruction that locked this entry, not inferred or guessed by the implementer — consistent with the "must not proceed with undocumented behavior" rule this entry carried while OPEN.
- **References.** `PROTEGE_ARCHITECTURE.md` §10.2; `packages/learning-engine/src/protege/learning_engine/{mastery_engine.py, constants.py}`.
- **Consequence.** `feature/p2-learning`'s `mastery_engine.py` implements exactly these two formulas, tested for deterministic behavior. See **D11** for implementation-level interpretive choices this lock does not cover, made during P2 and flagged for separate review — they are not part of this lock and remain open.

## D11 — P2 implementation interpretations flagged for review (informational, not locked, not blocking)

- **Status.** Informational. These are modeling choices made while implementing `packages/learning-engine` (P2) that go beyond what D10 or any canonical document specifies. They are implemented and tested — P2's own exit criteria do not depend on resolving them further — but they are not ratified architectural decisions. Whoever owns P6 (Diagnostician), P7 (FSM/orchestration), or P11 (policy) should review them before depending on this behavior.
- **Gap A — misconception belief normalization. SUPERSEDED by D13.** `PROTEGE_ARCHITECTURE.md` §10.2 gives `P(M_k|d) ∝ P(d|M_k)·P(M_k)` as a proportionality only; no document specifies the complementary likelihood `P(d | ¬M_k)` that a textbook two-outcome Bernoulli Bayes update would need — a distinct question from D10's "missing distractor entry" gap. `misconception_belief_update` resolved this, as first implemented, by normalizing across the **closed candidate set of misconceptions the caller supplies**: `posterior_k = P(d|M_k)·prior_k / Σ_j P(d|M_j)·prior_j`. **This has been rejected by adversarial review and by D13: candidate-set normalization contradicts §10.1/§10.2's explicit "independent Bernoulli" model rather than merely filling a silent gap in it.** D13 locks the actual required formula and the authored field this implementation is missing. This entry is kept for its historical record of what shipped first and why it was wrong; do not implement against it.
- **Gap B — Elo item/learner "win" convention and expected-score sign.** D10's locked formula is symmetric in `S` and does not say which side's correctness maps to `S = 1`, nor does it specify whether `E`'s `(R_item - R_learner)` exponent term is evaluated with `R_item` or `R_learner` as the entity being updated. A literal transcription (`R_item` first, verbatim) turns out to be self-defeating when driven through `R' = R + K(S-E)` with `S` read as the item's own score: it pushes an already-hard item's rating further up on a response that should make it look *easier* (verified empirically while implementing — see `test_elo_converges_toward_the_success_target_over_many_responses`, which fails under the literal sign and passes under the convention below). `update_item_elo`/`elo_expected_score` instead use the standard same-entity Elo convention — `elo_expected_score(a, b) = 1/(1+10**((b-a)/400))` is "probability `a` beats `b`" — with the item as `a`: the item "wins" (its rating rises) when the learner answers incorrectly, and "loses" (rating falls) when the learner answers correctly. This is the standard meaning of "item difficulty Elo" as a named technique and produces a stable, converging rating walk; it is not an arbitrary pick, but no PROTÉGÉ document states it, and the literal exponent order in the task instruction's formula text does not resolve it.
- **Gap C — source of `learner_rating`. RESOLVED (narrowed, not fully closed).** `PROTEGE_ARCHITECTURE.md` §10.2 scopes Elo to "item difficulty" only; mastery/ability in this system is tracked via BKT's `P(L)`, on an entirely different scale. Checked directly: neither §22's database register nor §11.2's 14-dimension policy context vector (which uses `P(L_s)`, `max_k P(M_k)`, hint rate, streaks, etc. — all probability-space, no Elo-scale quantity) contains any per-learner Elo-comparable rating anywhere. **Decision: P2 does not model a persisted per-learner Elo state, and none is implied by any canonical document.** The `learner_rating` parameter of `update_item_elo`/`elo_expected_score` is a **fixed reference rating** — a shared calibration point that lets *items* drift toward their true relative difficulty against a stable reference over time (consistent with "no cold-start item calibration needed"), not a personalized per-learner value. No BKT→Elo conversion is invented or required. **Still open:** roadmap P11's own text ("Item selection by Elo match targeting ~0.75 success") confirms Elo *is* intended to drive runtime item selection, but the exact algorithm combining an item's (population-calibrated) Elo rating with a learner's `P(L)` to hit that ~0.75 target is not specified by any document. **P11 remains responsible for defining exactly how item Elo is combined with `P(L)` for item selection** — this is not resolved here and must not be preempted by P2.
- **References.** `packages/learning-engine/src/protege/learning_engine/mastery_engine.py` (module and function docstrings carry the same notes at the point of implementation); `PROTEGE_ARCHITECTURE.md` §11.2 (14-dim context vector); `PROTEGE_IMPLEMENTATION_ROADMAP.md` P11 ("Learning engine" field).
- **Consequence.** Gap A is superseded by D13. Gap C is resolved for P2's purposes (no persisted learner rating; `learner_rating` is a fixed constant) but leaves the P11 selection algorithm explicitly open for that phase. Gap B (the Elo sign/win convention) is unaffected by this update and remains informational, as originally recorded.

## D13 — LOCKED: Independent Bernoulli misconception model

- **Status: LOCKED.** Resolves the P1 finding from adversarial review of `feature/p2-learning`: `misconception_belief_update`'s candidate-set normalization contradicts, rather than merely fills a gap in, the architecture's explicit misconception model.
- **Conflict/defect.** `PROTEGE_ARCHITECTURE.md` §10.1 states misconception belief is *"Bernoulli per misconception"*; §10.2 states *"Misconceptions: **independent Bernoulli beliefs**, Bayes-updated from a hand-authored likelihood table `P(response | M_k)`."* "Independent" is explicit and repeated, and is structurally required by §10.1 rule 1's `mastery_effective = P(L_s)·Π(1−P(M_k))` — a product of independent complements. The implementation shipped on `feature/p2-learning` instead normalized posteriors across a caller-supplied candidate set so that `Σ_k P(M_k|d) = 1`, which is categorical/multinomial, not independent-Bernoulli. This was disclosed (docs/DECISIONS.md D11 Gap A, as originally recorded) but disclosure does not make it correct, and it was never proposed as an accepted alternative — it is a defect to fix.
- **Decision — the formula.** For each tracked misconception `M_k`, computed **independently** (no normalization across other tracked misconceptions):

      P(M_k | d) =
        [P(d|M_k) * P(M_k)] /
        [P(d|M_k) * P(M_k) + P(d|not M_k) * (1 - P(M_k))]

  Candidate-set normalization (`posterior_k = score_k / Σ_j score_j`) is explicitly rejected as the mechanism for combining evidence across misconceptions attached to the same skill or item.
- **Decision — what `distractor_likelihood` means, and what it does not.** `Misconception.distractor_likelihood` represents **only** `P(d | M_k)` — exactly what its existing docstring already says, and exactly what the authored data's own shape confirms (e.g. the §38 worked example's `{"picks_1_8": 0.82, "says_equal": 0.06, "other": 0.12}` sums to 1.00, the signature of a distribution conditioned on **holding** `M_k`). The existing `"other"` entry is part of *that* conditional distribution's residual mass and **must not** be reused as `P(d | not M_k)` — doing so would use a value conditioned on holding `M_k` in the slot for a value conditioned on not holding `M_k`, a category error, not an approximation.
- **Decision — the new authored field.** A new field is required to supply `P(d | not M_k)`, since no currently-authored quantity in `packages/contracts` or any P3 content convention represents it (checked directly: `prevalence_prior` is the marginal `P(M_k)`, the wrong quantity; other misconceptions' own `distractor_likelihood` tables give `P(d|M_j)` for `j≠k`, not `P(d|¬M_k)`; `LearningItem.Distractor.likelihood` has no independent definition and its values match `Misconception.distractor_likelihood` exactly, indicating a denormalized copy, not a new source).
  - Proposed field name: **`distractor_likelihood_if_not_misconception`**.
  - Shape: `dict[str, Probability]` — identical shape to `distractor_likelihood`.
  - Semantics: conditioned on **not** holding `M_k`; uses the same behavior keys as `distractor_likelihood`; carries its own authored `"other"` residual bucket, independently summing to ~1.0 under its own conditioning.
  - Authoring: exact numeric values are authored by P3 (the same "authored, never learned" discipline §10.2 already applies to `distractor_likelihood`), never inferred, approximated, or learned at runtime.
- **Why this follows from the architecture.** `PROTEGE_ARCHITECTURE.md` §10.1/§10.2 explicitly specify independent Bernoulli beliefs and an authored (not learned) likelihood; this decision restores fidelity to both statements rather than trading one for the other, which is what the superseded candidate-set approach did.
- **Supersedes.** D11 Gap A in full (see that entry's updated text). Does not affect D10 (Elo, or the `"other"`-fallback convention for `distractor_likelihood` itself, which is unchanged) or D11 Gap B (Elo sign convention, unaffected).

## D16 — P9 persistence: append-only enforcement vs. learner-deletion cascades, embedding dimension sourcing, and event synthesis for the P8 bridge

- **Gap 1 — append-only vs. `ON DELETE CASCADE`/`SET NULL`.** The roadmap requires database-level append-only enforcement on `evidence`/`events`/`safety_events`, and separately requires learner deletion to cascade (hard-delete `evidence`) and to respect retention exceptions (`events`/`safety_events` survive, un-linked). Postgres implements `ON DELETE CASCADE` and `ON DELETE SET NULL` as an internal `DELETE`/`UPDATE` on the referencing row — exactly what a blanket `BEFORE UPDATE OR DELETE` trigger blocks, so the two requirements directly conflict for these three tables.
  - **Decision.** The append-only trigger function (`db/append_only.py`) checks one transaction-local GUC, `protege.allow_cascade_write`, before raising. Only `LearnerRepository.delete` sets it (`SET LOCAL ... = 'on'`, scoped to that one transaction, auto-reset at commit/rollback). Every other write path — including a direct `UPDATE`/`DELETE` attempt against `evidence`/`events`/`safety_events` from anywhere else — is still blocked. `tests/test_append_only.py` proves this by never setting the flag.
  - **Consequence.** `evidence.learner_id` is `ON DELETE CASCADE` (hard-deleted with the learner, matching "Parent-initiated deletion is hard delete"); `events.learner_id`/`session_id` and `safety_events.learner_id`/`session_id` are `ON DELETE SET NULL` (retained, un-linked — the roadmap's own "retention/audit exception" instruction, applied to the two tables §22 marks with multi-year retention).
- **Gap 2 — embedding dimension.** v1.0 §22's abridged DDL hardcodes `vector(1536)`; docs/DECISIONS.md D2 already supersedes this with a configuration-driven 384-d (`bge-small`), but D2 predates any actual migration/table existing to apply it to.
  - **Decision.** `Settings.embedding_dimension` (default 384) is read once, at import time, by both `db/models/memory.py` (the ORM column type) and the P9 migration (which creates `embedding_records` directly from that same ORM `Table` object) — one source, matching D2's "neither value may be hardcoded" requirement literally, not just in spirit.
- **Gap 3 — evidence provenance for a P8-shaped run.** P8's thin thread mints evidence with an opaque, in-memory `source_event_id` (`evt_001`, ...) but never constructs a real `DomainEvent` (P8 is explicitly "no DB, no event bus"). The roadmap requires "evidence rows retain `source_event_id`" and "claim -> evidence -> source event -> originating session/turn" to resolve by query, which needs a real persisted event row to point to.
  - **Decision.** `persistence/thin_thread_bridge.py` synthesizes one `events` row per evidence item at persistence time (event type inferred from `EvidenceKind`; occurred_at is a synthetic monotonic timestamp, since P8 does not timestamp evidence), plus `SESSION_STARTED`/`SESSION_COMPLETED` bookends. `evidence.source_event_id` is a real foreign key to that row's UUID; the original opaque P8 id is preserved as `external_ref` on both `events` and `evidence` for traceability. A real P10 service wired directly to role outputs (not through P8's demo return type) would construct genuine `DomainEvent`s at the point each thing actually happens, making this synthesis step unnecessary — see the bridge module's own docstring for the two disclosed fidelity limits this implies (transition `trigger` names, and event timing).
- **References.** `PROTEGE_IMPLEMENTATION_ROADMAP.md` P9 (Components, Testing, "APPEND-ONLY PROTECTION", "DELETION / CASCADES"); this document's D2 (embedding dimension); `packages/thin-thread/src/protege/thin_thread/ids.py` (P8's `IdAllocator`, the source of the opaque ids this entry's Gap 3 addresses); `services/session/src/protege/session_service/db/append_only.py`, `db/models/memory.py`, `persistence/thin_thread_bridge.py`.
- **Consequence.** None of P8's own code or contracts changed — this entry documents persistence-layer (P9) design choices made to reconcile requirements the roadmap states separately, not a reopening of any P1–P8 decision.
